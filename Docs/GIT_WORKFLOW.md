# Git workflow

Единственный подробный владелец политики веток, продвижения и версии. Остальные документы и
инструкции для агентов ссылаются сюда, а не пересказывают эти правила.

## Модель веток

- `integration` — накопительная PR-ветка: в неё сходятся проверенные рабочие ветки, deploy из неё
  не выполняется. Писать и коммитить в ней напрямую запрещено.
- `dev` — ветка dev-окружения; принимает неизменённый проверенный commit только из `integration`.
- `production` — ветка production-релиза; принимает неизменённый commit только из `dev`.
- Рабочую ветку создавай от актуального `origin/integration`. Любое изменение сначала делается в
  отдельной рабочей ветке; `integration`, `dev` и `production` не используются как локальные ветки
  разработки даже при намерении потом открыть PR.
- Единственный штатный путь: рабочая ветка → `integration` → `dev` → `production`. Переходы
  рабочая ветка → `dev`, рабочая ветка → `production` и `integration` → `production` запрещены.

Проекту без отдельных окружений достаточно `integration` как ветки по умолчанию; `dev` и
`production` появляются вместе с deploy.

## Имена рабочих веток

```text
feature-<scope>
fix-<scope>
docs-<scope>
test-<scope>
deploy-<scope>
qol-<scope>
```

Имя кратко описывает один scope и не содержит секретов и персональных данных.

## PR

- У каждого PR один понятный scope, критерии готовности и список рисков.
- Рабочая ветка мержится PR-ом в `integration` после CI.
- Продвижение выполняется отдельными PR `integration → dev` и `dev → production`; они переносят тот
  же проверенный commit и не повторяют тяжёлые проверки, уже обязательные для `integration`.
- PR создаёт и мержит разработчик.
- Несвязанные изменения с разными рисками разделяй на отдельные ветки и PR.

## Защита ключевых веток

Если доступны GitHub rulesets или Protected Branches, включи их для `integration`, `dev` и
`production`: обязательный PR, обязательные проверки, запрет force push и обхода правил.

Без них работает бесплатная мягкая защита из двух уровней. После каждого clone установи hooks:

```bash
uv run Scripts/setup_git_hooks.py
```

Скрипт задаёт локальный `core.hooksPath=.githooks` и проверяет `pre-push`, который блокирует push
в `integration`, `dev` и `production`. Его можно обойти через `git push --no-verify`, поэтому это не
граница безопасности. Workflow `Protected branch soft-guard audit` после каждого push в ключевую
ветку проверяет через GitHub API, что новый commit пришёл merged PR допустимого направления.
Нарушение означает, что изменение уже произошло: workflow падает и требует ручной проверки, но
ничего не откатывает.

CI проверяет направление каждого PR: в `integration` — только из рабочей ветки, в `dev` — только из
`integration`, в `production` — только из `dev`.

## Rebase

Рабочую ветку можно rebase поверх актуального `integration`, после чего допустим только безопасный
force push своей ветки:

```bash
git push --force-with-lease origin <branch-name>
```

Общие ветки без координации с участниками не переписываются.

## Версия

Решение о повышении версии принимает разработчик; агент меняет версию только по явному запросу.
Если проект версионируется, каждый рабочий PR в `integration` повышает версию в манифесте проекта
вручную, а promotion PR переносит ту же версию:

- PATCH — docs, QoL, fix и внутренний cleanup;
- MINOR — обратно совместимая новая функция;
- MAJOR — несовместимое поведение, миграция данных или контракт конфигурации и deploy.

## Границы агента

Агент готовит изменения, проверки и отчёт, но не выполняет commit, push, создание PR и merge.
Он продолжает подходящую ветку текущей задачи или создаёт новую от актуального `origin/integration`,
сохраняя незавершённую работу. Состояние проверяется так:

```bash
uv run Scripts/check_workspace.py --start --fetch   # перед созданием ветки
uv run Scripts/check_workspace.py                   # в рабочей ветке
```

Нельзя очищать, сбрасывать или прятать чужие изменения ради прохождения проверки.
